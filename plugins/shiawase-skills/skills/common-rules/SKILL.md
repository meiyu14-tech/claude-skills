# 共通ルール（common-rules）

全スキル・全作業に適用する共通ルール。目的は3ム（無理・無駄・ムラ）をなくし、
Claude CodeとCoworkがどの環境でも同じ動きをすること。
個別スキルのルールと矛盾した場合は、このファイルを正本とする。

## 作成前

### 項19：どこで作業するかを最初に決める（コワークとコードの使い分け）

**続きが発生しない単発の成果物づくりだけコワーク。それ以外はすべてコード。**

| 環境 | 使う場面 |
|:---|:---|
| **コワーク** | 1回で完結する資料づくり（この会話の中で作って渡して終わり） |
| **コード** | 上記以外すべて。**続きがある作業・記録（正本）を触る作業・複数回にわたる相談** |

**理由：コワークは会話の履歴を次回に引き継げない。** さらに扱える情報量が上限に達すると、そこで打ち止めになる。
一方コードは、上限に近づくと自動で要約して続行でき、**過去のセッションを横断して検索できる**（「あの話どこでしたか探して」と言えば見つかる）。

**⚠️ 迷ったらコードを選ぶ。** 単発のつもりで始めた作業が続いたとき、コワークだと**それまでの経緯が全部消える**。コードで始めておけば損はしない。

**背景（2026-08-04）：** コードは動作が重いためコワークで作業したところ、情報量が上限に達して結局遅くなり、
そのうえ履歴を引き継げず、コードに戻ってやり直すことになった。**遅さを避けてコワークへ移ると、二重に時間を失う。**

### 項0：壁打ち（認識合わせ）必須

1. 成果物を作る前に、必ず「**目的・完成形のイメージ・保存先**」の3点を短く提示し、伊藤さんに確認する
2. 認識が合ってから（OKをもらってから）作成に取り掛かる。合わないまま作り始めない
3. ズレていた場合は直してもう一度確認する（合うまで作らない）
4. 例外：既存ファイルの軽い修正は「この点をこう直します」と変更点を先に見せるだけでよい（誤字修正レベルのみ返事を待たず着手可）

#### 項0-1：見た目を変えるときは、先に「文字で完成形」を書く

**画面・書類の見え方（並び・番号・ラベル・リンクの有無）を変える指示を受けたら、コードやファイルに触る前に、完成形を文字で1回書いて見せる。**

```
✓ ⑤-1  経営OSの導入の流れ        ← 押せる
   ✓ ⑤-1-6  打ち合わせの進め方    ← 文字だけ
```

この3〜5行があれば1往復で決まる。無いまま作ると、**作る→違う→作る**を何度も繰り返す。

**⚠️ 伊藤さんが挙げる具体例は「例え」であって「仕様」ではない。**
`OS-03-02-01-MTG-001` のような例を見せられたとき、**その形をそのまま実装してはいけない。**
「この考え方で、いまのVaultに当てるとこう見えます」と**完成形に翻訳して**確認する。

**⚠️ 「変わってません」と言われたら、直す前に「どの画面を見ているか」を聞く。**
同じ内容が複数の場所に出ている（例：ファイル名／`<title>`／`<h1>`／一覧の表示名／「位置：」欄／台帳）。
推測で1つずつ直すと、相手が見ている場所に当たるまで何往復もかかる。

**背景（2026-07-30）：**業務フローの番号の見せ方を決めるのに**10往復以上**かかった。原因は上の3つ（例えを仕様として実装した／完成形を見せずに作った／どの画面かを聞かずに推測で直した）。**項0は元からあったが、実装を急いで飛ばした。**見た目の変更は特に飛ばしやすいので、ここに独立した項として書き出す。

### 項8：既存確認（二重作成の防止）

- 作る前に、似た成果物・似たスキルがすでにないか検索する
- あれば新規作成せず、追記・修正で対応する
- 確認先：Vault内の該当フォルダ・`成果物マスター.md`・スキル一覧

### 項10：質問の上限

- 不明点の質問は**最大3問**まで
- それ以上は「**（推定）**」付きで補完して先に進み、推定箇所を報告に明記する

## 作成中

### 項5：ファイル命名

- 形式：`YYYY-MM-DD_内容.拡張子`（日付が不要な定義ファイルは内容名のみ）
- スペースなし（`_`でつなぐ）・略語なし・ファイル名だけで中身がわかること
- 同名ファイルがあれば `_1` `_2` と連番を付ける

### 項6：機密の扱い

- 個人名・金額・契約内容・原発/廃炉関連の固有名詞を含む成果物は、報告に「**機密情報を含む**」と明記する
- スキル本文（GitHubに置くファイル）には機密情報を一切書かない
- 公開/機密で迷ったら必ず機密として扱う

### 項12：名称の統一

- 同じものを指す言葉は、Vault・スキル・成果物すべてで1つに統一する（例：「取扱説明」と「マニュアル」を混在させない）
- 不統一に気づいたら、AIが自分で直してから報告する（伊藤さんに指摘させない）

### 項14：書類の冒頭に「この書類の使い方」を必ず置く

**すべての成果物（Markdown・Excel・HTML・Word等）の一番上に、以下4点のブロックを置く。** 目的は、誰が読んでも解釈がぶれないようにすること（ムラなし）。

| # | 項目 | 書く内容 |
|:---:|---|---|
| 1 | **この書類は何か** | 1行で定義する（例：「この事業・プロジェクトをやるかどうかを判断するための書類です」） |
| 2 | **何のために使うか** | この書類があると何が決まるか・何が防げるか |
| 3 | **誰がいつ使うか** | 読む人と、読む場面（例：「新しい企画を思いついたとき／やるか迷ったとき」） |
| 4 | **使い方** | どう読み、どう書き換え、どう判断に使うか。3〜5行 |

**書き方のルール：**
- 中学生でもわかる平易な日本語。専門用語は初出時にかっこ書きで説明する
- 本文（中身）より先に置く。目次より前でよい
- Markdownなら `## この書類の使い方` セクション、Excelなら先頭シートまたは冒頭行、HTMLならページ最上部に置く
- 「あとで書く」はしない。書類を作るのと同時に書く
- 既存書類を編集するとき、このブロックが無ければ**その場で追加する**（伊藤さんに指摘させない）

## 納品（保存と手渡し）

### 項9：動作確認してから渡す

- 成果物は必ず自分で開いて確認してから渡す（Excelが開くか・HTMLが表示されるか・コードが動くか）
- 確認した内容と結果を報告に含める。未確認のまま「できました」と言わない

### 項1：保存先

| 成果物の種類 | 形式 | 保存先 |
|---|---|---|
| Wiki文書（記録・議事録・ノート類） | **Markdownのみ**（Office形式で書かない） | Vault内の該当フォルダ |
| 人に渡す道具（SOP・取扱説明フロー等） | 用途に合った形式（Excel・HTML等） | Vault内の専用フォルダ（`SOP/`・`取扱説明/`等） |
| コード | ソースコード | GitHubリポジトリ（Vaultの進捗ノートにリンクを記録） |

- Vaultのパス：`G:\マイドライブ\ObsidianVault\MyVault\幸せ貢献業\`
- **Markdown以外の成果物は必ず `成果物マスター.md` に記録する**（日付・書類名・保存先・区分）。これで全成果物がObsidian検索から見つかる
- **Gドライブに手が届かない環境（Coworkのクラウド実行等）の場合**：ファイルを伊藤さんに直接手渡し（送付）し、報告に「⚠️ Vault未保存。受け取って保存してください」と明記する
- **すべての成果物は、Vaultに保存すると同時にダウンロードフォルダ（`C:\Users\user\Downloads`）にも同じファイルをコピーする。** 伊藤さんがすぐ手に取れる状態にするため。Vaultが正本、ダウンロードフォルダは受け取り用の控え
  - **例外：追記型の台帳ファイル**（成果物マスター・学びたいこと台帳など、1行ずつ足していくもの）は控えを作らない。毎回コピーすると同じファイルが溜まるだけで役に立たないため
- **⚠️ ダウンロードフォルダに置くファイル名を `CL_` で始めてはいけない。** 受け皿監視スクリプトが取り込んで別フォルダへ移動してしまうため（通常の `YYYY-MM-DD_内容.拡張子` 形式なら問題ない）
- 伊藤さんのPCでファイルを手渡すとき（手順書・一時ファイル等）も、デスクトップではなくダウンロードフォルダに置く
- 保存しただけでは渡したことにならない。必ず**項15**を実行する

### 項15：保存して終わりにしない。必ず伊藤さんの手元に届ける

**成果物を保存したら、同じ返信の中で伊藤さんがその場で開ける形にして渡す。**
「Vaultに保存しました」＋ファイルパスの提示だけで終わらせてはいけない。

**Vault保存と手渡しは目的が違う。両方やる。**

| 動作 | 目的 |
|:---|:---|
| Vaultに保存する | **記録のため**（次のセッション・別のPC・検索から到達できるようにする） |
| 伊藤さんに手渡す | **読んでもらうため**（保存しただけでは伊藤さんの目に触れない） |

**渡し方（上から順に試す）：**

1. **チャット画面にファイルを直接送る**（Claude Code：`SendUserFile` ツール）。最優先。伊藤さんの操作がゼロで済む
2. 1が使えない環境では、ダウンロードフォルダ（`C:\Users\user\Downloads`）にコピーを置き、ファイル名を伝える

**注意：** ダウンロードフォルダに置くファイル名を **`CL_` で始めない**。Claude受け皿監視スクリプトが `Downloads` 内の `CL_` で始まるファイルを自動で取り込んで移動させるため、渡したはずのファイルが消える。

**背景（2026-07-25）：** 熱中症対策の企画書・要望書をVaultに保存したが、伊藤さんの手元に届けなかったため「企画書を確認できていません」と指摘を受けた。項1（Wiki文書はVaultへ）には従っていたが、**ルールに従った結果として成果物が届かなかった。** 保存先のルールと手渡しのルールは別物である。

### 項16：伊藤さんに「探させる」状態を作らない

**「〜に開いてあります」「〜に置きました」で終わらせてはいけない。伊藤さんが場所を探す必要がある時点で、渡せていない。**

**特に禁止：AIにしか見えない場所に成果物を置き去りにすること。**

| 置き去りにしがちな場所 | なぜ駄目か |
|:---|:---|
| **ブラウザパネル（Browser / preview）** | AIの作業画面であり、伊藤さんは毎回どこにあるか分からない。**「ブラウザ画面を見てください」は案内になっていない** |
| ターミナルの出力 | 流れて消える |
| Vaultの奥のフォルダ | パスを伝えても開くまでに手数がかかる |
| 私が開いた一時的な画面・セッション | 次に見たときには消えている |

**必ず守ること：**

1. **成果物は伊藤さんの手元で完結する形にする。** ファイル（`SendUserFile`）か、そのままクリックできるURLのどちらかで渡す
2. **ブラウザ操作の結果を成果物にしない。** ブラウザで作業した場合も、その中身を**ファイルに書き出して手渡す**。画面の場所を言葉で説明しない
3. **到達に2手以上かかるものは、渡し方を作り直す。** 「パネルを開いて、スクロールして、その欄を見て」は失敗
4. Webフォームへの入力など、伊藤さん自身の操作が必要な作業では、**貼り付ける内容をコピーボタン付きのHTMLファイルにして渡す**（クリップボード経由の失敗も同時に防げる）
5. **そのHTMLは、ダウンロードフォルダに置いたうえで `Start-Process` で伊藤さんの既定ブラウザに開かせる。** Claudeのブラウザパネルで表示させて終わりにしない

**⚠️ ブラウザパネルの制約（2026-07-25 確認）：** Claudeのブラウザパネルは **localhost 以外の外部URLを開けない**。パネル内に表示したHTMLに外部リンクを置いても「Link to ... was blocked」となり機能しない。**外部サイトへ誘導する成果物は、必ず伊藤さんの既定ブラウザで開くこと。**

**背景（2026-07-25）：** 厚労省の意見フォームに要望文を入力する際、AIのブラウザパネル上でフォームに記入し「ブラウザ画面に開いてあります」と報告した。伊藤さんから「毎回どこか分かりません」と指摘を受けた。**AIから見えていることと、伊藤さんから見えていることは違う。** 項15（保存して終わりにしない）と同じ失敗を、保存先ではなく作業画面で繰り返したもの。

## 報告

### 項2：返信フォーマット

- 返信は必ずAI識別子＋報告IDで開始する。冒頭からフォーマットが消えるのはNG
- Claude Code：`Claude Codeからの返信:` ＋ `CC-YYYYMMDD-XXX`
- Cowork：`Coworkからの返信:` ＋ `CW-YYYYMMDD-XXX`
- すべての見出し・内容をその配下に含める

### 項3：報告の型（5点フォーマット）

報告は以下の5点のみ。要約だけでよく、長文にしない。

1. 実装内容
2. 価値対応（何の目的・価値に応えたか）
3. 動作確認（何をどう確認したか）
4. 懸念点
5. 次タスク

### 項4：判断を仰ぐ型（6項目形式）

伊藤さんに選択・判断を求めるときは、番号で回答できる形にして以下をセットで添える。

1. 番号付きの選択肢（2〜4案）
2. 推奨案の明示
3. 理由（伊藤さんの目的・背景に紐づける）
4. メリット
5. デメリット
6. 所要時間

わかりやすい例え（アナロジー）も添えると良い。

#### 項4-1：「はい／いいえ」の小さな質問にも必ず推奨と理由を付ける

**大きな選択肢の提示だけでなく、報告の末尾に添える一言の確認・技術的な可否の質問・専門用語を含む質問にも、例外なく推奨と理由を付ける。**

| ❌ してはいけない聞き方 | ✅ 正しい聞き方 |
|:---|:---|
| 「合流してよいか教えてください」 | 「**合流を推奨します。**理由は〜。中身は〜で、失敗しても〜で元に戻せます。よろしければ『はい』とだけお答えください」 |
| 「この方式でいいですか？」 | 「**A案を推奨します。**理由は〜。B案との違いは〜」 |
| 「削除して問題ないですか？」 | 「**削除を推奨します。**中身は〜で、〜に同じものが残っています」 |

**判断に必要なものを、質問と同時に全部渡す。** 伊藤さんが調べたり考え込んだりしなければ答えられない質問は、質問として不完全である。

**必ず添える4点：**

| # | 添えるもの | 目的 |
|:---:|---|---|
| 1 | **推奨（どちらを勧めるか）** | 迷わせない |
| 2 | **理由** | 納得して決められる |
| 3 | **専門用語の意味を1行で** | 用語が分からないだけで判断できない状態を作らない |
| 4 | **失敗したらどうなるか／元に戻せるか** | リスクの大きさが分かる |

**背景（2026-07-26）：** ブランチ名統一の作業報告の末尾で「masterへの合流の可否を教えてください」とだけ聞き、推奨も理由も付けなかった。伊藤さんから「**素人のため判断のしようがありません**」と指摘を受けた。

**前提として持つべき認識：** 伊藤さんは技術の専門家ではない。**AIが決めた名前・方式・用語について裏取りをしていない。** したがって「AIが勝手に決めたこと」を前提にした質問は、そのままでは答えられない。**意味の説明から入り、推奨で締める。**

**それでも判断を求めてよい／求めるべき場面：** 不可逆な操作（削除・公開・送信・課金）、方針・優先順位、お金の使い方、外部に出る内容。これらは推奨を付けたうえで必ず聞く。逆に、**技術的な実装方法や、やり直しが効く作業は聞かずにAIが決めて実行し、結果を報告する**（CLAUDE.md「Claudeが自分で判断して動ける場面は結果を報告するのみ」）。

### 項18：報告は判断に必要な最小限だけにする（項3・項4より優先）

**背景（2026-07-27）：** 伊藤さんから「**毎日10時間以上あなたと壁打ちするおかげで、出力された文字を読み判断するということで頭を使いすぎて自律神経が乱れています**」と共有があった。**報告の長さそのものが体調を損なう負荷になっている。読む量を減らすことは好みではなく健康の問題。**

**チャット本文に書いてよいのは、次の3つだけ。**

| 順 | 内容 | 分量 |
|:---:|---|---|
| 1 | **判断してほしいこと**（無ければ書かない） | 1〜3個・各1行。答えは「はい／いいえ」か番号 |
| 2 | **すでに済ませたこと** | 1行 |
| 3 | **詳細ファイルへのリンク** | 1行。「読まなくて構いません」と添える |

分析・根拠・経緯・実測値の一覧・実装の説明は**本文に書かない。**

#### 項3・項4との関係（廃止ではなく、置き場所を変える）

| ルール | どう変わるか |
|:---|:---|
| 項3（5点フォーマット） | **詳細ファイル側の型**にする。チャット本文には出さない |
| 項4・項4-1（推奨・理由・メリット・デメリット・所要時間） | **考え方は廃止しない。**伊藤さんは技術の専門家ではないので、判断材料が要ることは変わらない。ただし**チャットに書くのは「推奨＋理由1行」だけ**にし、残りは詳細ファイルへ移す |

**⚠️ 前提として、判断を求める回数そのものを減らす。**
やり直しが効くこと・技術的な実装方法は**聞かずに決めて実行し、結果を1行で報告する**（項4末尾の規定どおり）。
聞いてよいのは **不可逆な操作・お金・外部に出る内容・方針と優先順位** の4つだけ。

#### 折りたたみ（プルダウン）の作り方

**チャット本文では折りたたみが効かない。**端末上のマークダウン表示のため `<details>` は無視される。

→ **折りたたんで見せたい内容は、HTMLファイルにして渡す。**HTMLなら携帯でも効く。

```html
<details><summary>見出しだけ見て、要らなければ開かない</summary>
ここに詳細を書く
</details>
```

渡し方は項15・項16に従う（ワンクリックで開ける形にする。場所を説明して探させない）。

#### 体調不良の共有があった日

**その日は判断を求めない。**私の判断で進め、結果を1行で報告する。「任せます」と言われたら、不可逆・お金・外部送信を除いてすべて自分で決めて実行する。

### 項11：操作依頼は①②③形式

- 伊藤さんに操作をお願いするときは、番号付き（①②③）・1ステップ1アクションで示す
- コピー&ペーストだけで済む形が理想。長い説明文の中に操作を埋め込まない

### 項13：操作を依頼する前に自分でできないかを必ず検証する

**伊藤さんに何かの操作を頼む前に、以下を全部確認する。1つでも未確認なら依頼してはいけない。**

1. **使えるツールを実際に探したか**：ツール一覧に出ていないだけで「できない」と判断しない。ブラウザ操作（Claude in Chrome）・PC画面操作・セッション連携などは、呼び出す前に検索が必要な場合がある。検索せずに「私にはできません」と言うのは禁止
2. **画面操作だから人間の仕事、と決めつけていないか**：Web画面（claude.ai・管理画面・SaaS）はブラウザ操作ツールで私が直接操作できる。スクリーンショットを見せられても「操作を案内するモード」に入らず、「私が操作を代行するモード」で考える
3. **承認が必要な操作と、単に画面を触るだけの操作を混同していないか**：承認が必要なのは不可逆操作・課金・アカウント設定変更・外部送信のみ。画面を開く・一覧を見る・インストールする・テストを走らせるは私が黙って実行する

**それでも依頼が必要な場合の条件：**
- 物理的に私が到達できない（インストール版アプリ内の操作・ネイティブのファイル選択ダイアログ・パスワード入力）
- または、セキュリティ原則で私が触ってはいけない操作
- 依頼するときは「なぜ私ではできないのか」を1行で必ず添える

**背景（2026-07-25）：** スキル基盤構築時、ブラウザ操作ツールを検索せずに「プラグイン追加は伊藤さんの操作」と決めつけ、同じ作業を何度も伊藤さんにやらせた。ツールを検索した後は全て私が代行できた。「知らないからできない」は許されない（CLAUDE.md行動ルール）。

### 項15：開く先があるものは必ずワンクリックで開けるようにする

**報告や成果物の中で何かを参照させるときは、伊藤さんが探さずに1回で開ける形にする。** 場所を文字で説明して探させない。

| 対象 | ワンクリックの形 |
|---|---|
| Trelloカード | カードのURL（`https://trello.com/c/xxxxxxxx`）をリンクにする |
| Vault内のファイル（チャット内で示すとき） | Vaultルートからの相対パスでマークダウンリンクにする（例：`[学びたいこと台帳](情報/学びたいこと台帳.md)`） |
| **Vault内のファイル（携帯・メール・Trello・チャット外に出すとき）** | **Google DriveのURLを付ける。** Drive検索（`title contains '<ファイル名>'`）で `viewUrl` を取得して使う。相対パスは携帯から開けないため |
| Webページ・動画 | URLをそのまま載せる |
| 作成したTrelloカード・ラベル | 報告の中でカード名をリンクにする |

**⚠️ 操作を依頼するときも同じ（項11と対で必ず守る）：**

伊藤さんに何かの操作をお願いするときは、**その画面への直リンクを必ず添える**。

- ❌ 「いま開いている画面で『Trello』の＋を押してください」
- ❌ 「設定 → コネクタ → Trello を探して連携してください」
- ✅ 「[この画面を開く](URL) → 『Trello』の＋を押す」

「いま開いている画面で」は禁止。伊藤さんがその画面を閉じていたら探し直しになるため。**リンク＋押す場所の1行**をセットにする。

**⚠️ claude.ai内の設定画面（`https://claude.ai/...#settings/...`）はチャット内のリンクを押しても開かない。** 検証済み（2026-07-25）。
この場合はリンクを出さず、**ブラウザ操作ツールで私がその画面を開き、押すボタンが見える状態にしてから依頼する**。「開きました。◯◯を押してください」が正しい形。

**やってはいけないこと：**
- `G:\マイドライブ\...` や `C:\Users\...` のような**生のパスだけを書いて終わりにしない**。書く場合もリンクを併記する
- 「◯◯フォルダに入っています」と場所だけ伝えて終わらない
- 開く先が無いのにリンクがあるように見せない（存在しないファイルへのリンクを作らない）

**理由：** 探す時間はゼロにできる。特に携帯では階層をたどるのが苦痛で、たどれない場所にあるものは結局使われない。

### 項16：新しいプロジェクトが生まれたら、その場で正本に登録する

**プロジェクトのフォルダ・引き継ぎノート・進捗ノートを新しく作ったら、同じ作業の中で `プロジェクト/プロジェクト一覧.md` にも1行追加する。** 「後で登録する」はしない。

登録する内容：プロジェクト名／フェーズ／担当／期限／詳細ファイルへのリンク

**フェーズの選び方（一覧の定義に従う）：**
- **構想**：アイデア・目的が発生した段階。実行判断前 ← **やるか決まっていないものはここ。登録しない理由にはならない**
- 調査 → 設計 → 実装 → 運用 → 完了

**背景（2026-07-25 判明）：** 録音判断ダッシュボード（7/13）・現場メモAI（7/14）・困りごとヒアリングAI（7/16）の3件が、正本に載らないまま数か月動いていた。原因は、CLAUDE.mdの規定が「**フェーズ変更**があれば一覧も更新する」となっており、**ゼロから生まれたときの規定が無かった**こと。加えて、開発作業に集中しているセッション内では「全体の台帳に載っているか」という視点が出てこないため、誰も気づけなかった。

**なぜ重要か：** 一覧に載っていないプロジェクトは、経営ダッシュボードにも朝の報告にも出てこない。**存在しないものとして扱われ、判断から漏れる。**

### 項17：業務フロー・手順書は、そのまま他社へ渡せる形で書く

**個人名と一人称を書かない。** 作った資料は、いずれ他の会社へそのまま導入する前提で書く。

| 書かないもの | 代わりに使う言葉 |
|:---|:---|
| 個人名（「◯◯さん」） | **承認者**（内容の正誤に責任を持ち、承認を押せる唯一の人） |
| 社員・作業者 | **担当者**（日々その仕事をし、食い違いを最初に見つける人。指示は出せるが承認はしない） |
| 私・自分・AIの製品名 | **チャット**（会話して調べる）／**コワーク**（資料を作る）／**コード**（ファイルとサーバーを直接さわる）から選ぶ |
| 会社名・URL・IPアドレス・端末名・リポジトリ名・保存先パス | **冒頭の「この会社の設定」欄に集め、本文からは番号で参照する**（`設定⑤` など） |

**「この会社の設定」欄は必ず置く。導入時はここだけ書き換えれば動く状態にする。**

**⚠️ 最初からこの言葉で書く。** あとから置換すると、印刷を1枚に収め直す作業が全部やり直しになる（2026-07-26に6枚分やり直した）。

**背景：** 自社用と配布用を2本持つと必ずずれる。正本は1本にして、違いは設定欄だけに閉じ込める。

### 項19：作る前に、誰が何をするかを1枚にして承認をもらう

**順番を守る。飛ばすと、承認が後付けの儀式になる。**

| 順 | やること |
|:---:|:---|
| **1** | **地図**：その会社の仕事の流れ全体を1枚にし、**いまどこが切れているか**を色で示す |
| **2** | **優先順位**：地図を見ながら、**承認者と一緒に**「どこから直すか」を決める |
| **3** | **フロー**：その業務だけを1枚にする（誰が何をするか。現状と、直した後） |
| **4** | **承認**：承認者が「これで合っている／ここを直す」を押す |
| **5** | **システム**：**承認された範囲だけ**を作る |
| **6** | **再承認**：動かして、フローを直して、もう一度承認をもらう |

**⚠️ 5を先にやらない。** 作ってから承認をもらう形にすると、承認者は**もう出来ているものに○を付けるだけ**になり、中身を見なくなる。**それでは承認の仕組みを実証したことにならない。**

**⚠️ 1を飛ばさない。** 地図が無いと、目についた所から直すことになり、**効果の薄い所に手が入る。**どこを直すかを**選べる状態にすること**が地図の役目。

**⚠️ 地図は最上位ではない。**地図の上に**理念・目的**（何のための会社か）がある。地図は「どうやるか」しか語れず、**「やるべきか」は理念にしか聞けない。**地図を最上位に置くと、**やらなくてよい仕事まで効率化してしまう。**

段の構造は **0 理念・目的 → 1 地図 → 2 業務フロー → 3 システム → 4 記録**。**記録は0と1へ戻す。**

**例外：**信頼を作るための**小さな道具**（相手の手元だけで完結し、1か月で効果が出るもの）は3より前に作ってよい。
ただしそれは「打ち手」であって「システム」ではない。**入力画面・人と共有される画面・記録が貯まるものは、すべて4の後。**

**背景（2026-07-28）：**1社目で、コードが**いきなり入力画面から作ろうとした。**承認者の指摘で気づいた。
**AIは「早く手を動かす」方向に寄りやすい。**（実際このときも、別のAIの「最初の1か月で実感を出す」という助言に引かれて順番を崩した）。
**寄りやすいからこそ、順番はここに書いて縛る。**

### 項20：自社の手順書と、顧客に見せる資料を混ぜない

**書類は「誰が読むか」で3つに分かれる。作る前にどれかを決める。**

| 種類 | 読む人 | 例 |
|:---|:---|:---|
| **自社の手順** | 自分たちだけ | 導入の進め方・開発サイクル・受け皿の仕組み |
| **顧客と一緒に見る資料** | **顧客の承認者・担当者** | 地図・業務フロー・見立てシート |
| **顧客に渡して終わる資料** | 顧客 | 提案書・引き渡し書 |

**⚠️ 顧客が読む紙に、自社の手順書の名前や番号を書かない。**

理由は2つ。
1. **相手はその書類を持っていない。**「◯◯フローのステップ6」と書いても、開けないので意味が分からない
2. **こちらの進め方が透ける。**顧客が知りたいのは自分の会社のことであって、こちらの段取りではない

**⚠️ 顧客が読む紙は、その1枚だけで完結させる。**
他の紙を開かないと分からない書き方をしない。**位置を示したいときは、番号ではなく「段の名前」で書く**（段0 理念・目的／段1 地図／段2 業務フロー／段3 システム／段4 記録＝項19）。

**⚠️ 作る前に読み手を宣言する。**業務フローHTMLなら `<meta name="flow-audience">` に `社内` か `社外` を書く。**`社外` ＝ 顧客が読む**。

**背景（2026-07-28）：**顧客に見せる地図に「自社の導入手順（フロー7）のステップ6」と書いてしまい、
承認者から**「どれのことか分からない」**と指摘された。**作っている側は全体が見えているので、混ざっていることに気づけない。**
**気づけないからこそ、読み手を先に宣言して分ける。**

## 禁止事項（項7）

- **生ソース（議事録原文・メール原文）の編集禁止**。参照のみ
- **内容を確認せずの上書き禁止**。既存ファイルは読んでから編集する
- Vault内のWiki文書をOffice形式（docx/xlsx/pptx）で作らない
- スキル・成果物に機密情報を書いてGitHubに置かない

## このルール自体の育て方

- **ルールはこのファイルに書く。メモリには書かない**（二重管理の防止。メモリに書くと片方だけ古くなる）
- 問題が起きるたびに、該当する項へ追記する（削除せず積み上げる）
- 変更したら必ずGitHubリポジトリ（claude-skills）にコミット・プッシュする
