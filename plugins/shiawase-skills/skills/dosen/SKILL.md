# 導線（設計図 → フロー → マニュアル → 実行 → 評価）

> **2026-08-21、伊藤さんとの一問一答で7点すべて合意した内容。** ここが正本。
> 個別の作り方は `gyomu-flow`（フローHTML）・`zukai`（取扱説明）・`sop`（SOP）を見る。

---

## なぜこれが要るか

**上から下へ降りた先で人が行動し、その結果が評価に戻ってくる。この一本が切れていなければ、評価と育成は自動で回る。**
逆に、どこか1か所でも切れると、そこから下は「作ったが誰も見ていない資料」になる。

---

## 1. 縦と横（合意①）

| 軸 | 中身 |
|:---|:---|
| **縦＝降りる階層** | 思想 → 理念 → ビジョン → 6つの価値 → 事業 → プロジェクト → タスク |
| **横＝経営資源の分類** | 人・物・金・情報。**どの階層にも横断してかかる**（階層ではない） |

**⚠️ 横の4分類を階層として扱わない。**保存先の分類であって、上下関係ではない。

## 2. 経営設計図は「目次」（合意②）

**設計図は階層そのものではなく、階層を見るための入口。**中身の正本はフローとマニュアルの側にある。
設計図に並ぶ番号（`⑤` `⑦` など）が、**そのままフローの住所**になる。

## 3. フローとマニュアルの関係（合意③）

| もの | 役割 |
|:---|:---|
| **フロー** | 誰が・何を・どの順でやるか（**流れ**。1枚で全体が見える） |
| **マニュアル**（取扱説明・SOP） | その**1つのステップ**を実際にどう操作するか（**やり方**） |

**フローの「1ステップ」に、必要なものだけマニュアルがぶら下がる。**（1対1にしない。人が操作するステップにだけ付く）

### 番号の付け方（導線はここで決まる）

```
⑦-4-6            業務フロー（設計図の⑦から降りた住所）
⑦-4-6-M3         そのフローの「ステップ3」のマニュアル
```

- **マニュアルのファイル名は、必ず親フローの番号 ＋ `-M<ステップ番号>` で始める**
- 番号を付けずにマニュアルを作らない。**番号が無い＝住所が無い＝導線に載らない**
- フロー側は、そのステップの **How欄からマニュアルへリンクする**（下の5W2H参照）

## 4. 5W2Hはフローのステップの欄（合意④）

**5W2Hはマニュアル側ではなく、フローの1ステップごとの欄として持つ。**

| 欄 | 中身 |
|:---|:---|
| Who | 誰が（承認者／担当者／AI） |
| What | 何をする |
| When | いつ・いつまでに |
| Where | どこで（どの画面・どの場所） |
| Why | なぜ必要か |
| **How** | **どうやって → マニュアルへのリンク**（無ければ空欄） |
| How much | どれだけかかるか（時間・費用） |

**⚠️ Howを空欄のままにしてよい。**空欄が「マニュアルがまだ無いステップ」を自動で教えてくれる。
**別の場所に書くと、欠けていても気づけない。**

## 5. PDCAの持たせ方（合意⑤）

| | 何に当たるか | 置き場 |
|:---|:---|:---|
| **P 計画** | フローそのもの（5W2Hの欄） | 業務フローHTML |
| **D 実行** | **誰が・いつ・どのステップをやったか** | 実行の記録（**要開発**） |
| **C 評価** | Dと、フローで決めた基準（期限・所要・完了判定）との突き合わせ | 自動 |
| **A 改善** | 気づき（変更指示）→ フロー・マニュアルの改訂 | 承認記録＋改訂履歴 |

**⚠️ Dはステップ単位・人単位で残す。**案件単位では評価に使えない。

## 6. 評価（合意⑥）

**評価の単位は「フローのステップ」。**

### 4つの力の見分け方

**その人の行動が、どこまで届いたかで決まる。**

| 力 | 判定の芯 | 例（AIメール秘書「AIが仕分ける」のステップ） |
|:---|:---|:---|
| **できる** | **自分の中で終わった** | 画面を見て「注文確認が広告に入っている」と間違いを見つけて指摘した |
| **教えられる** | **他の人に移った** | 「自分が注文した確認メールは広告ではない」を判定の指示文に書き加えた |
| **環境を作れる** | **次の人が困らない状態を作った** | テスト用のメール9通を用意し、誰がやっても同じ条件で確かめられるようにした |
| **仕組みにできる** | **そのステップ自体を消した** | 「渡す前に自分で実行する」を道具に埋め込み、確認する仕事そのものを無くした |

### 測り方（3つの数字）

| 数字 | 意味 |
|:---|:---|
| **①周回数** | そのステップが「気づき → 改訂」を何回通ったか |
| **②ノウハウ化** | 改訂後、**同じ問題の指摘が出なくなったか**（人の頭からフローの文面に移った） |
| **③定着** | 改訂後、**実際にやり直しゼロで回ったか**（Dが要る） |

**⚠️ 回数が多い＝良い、ではない。**同じステップで指摘が出続けているのは「回っている」のではなく「直せていない」。
**②まで見て初めてノウハウ化と言える。**

## 7. 誰がやったかの記録（合意⑦）

**端末で分ける。**段階で分けない。

| 使う場所 | 方式 | 記録の重み |
|:---|:---|:---|
| **個人の携帯**（ホーム画面のアプリ） | ログイン（**初回1回だけ**。以後自動） | **確定**（評価に使える） |
| **共有のパソコン・現場のタブレット** | 名前を選ぶ | **選択**（印を付けて区別。参考値） |
| **承認**（送信・公開・お金） | **ログインのみ。共有端末からは押せない** | 確定 |

**理由：**個人の携帯にアプリとして入れれば、ログインの手間は初回だけになり、**本人確定と使いやすさが両立する。**
共有端末では前の人の名前が残る事故が避けられないため、**評価に使う記録と参考の記録を最初から見分ける。**

**⚠️ 認証を1つ増やすだけで人は止まる。**（実測：合言葉がカタカナで携帯から入力できず、画面は4回開かれたのに登録0件。**止まったことはこちらからは見えず、原因究明に丸1日かかった**）
だから**承認以外は緩く、承認だけは固く**する。

## 8. フィードバックが返る仕掛け（必須）

**「あなたが出した指摘は、こう直りました」が本人の画面に返ること。**
返らないと2回目の指摘が出てこない＝PDCAが1周で止まる。

**⚠️ 2026-08-21時点で、この仕掛けは無い。**対応済みの記録はVault内にあるだけで、出した人には何も返っていない。

## 作る順番（上から。下は上が無いと測れない）

| 順 | 作るもの | 完了の判定 |
|:---:|:---|:---|
| **1** | フローとマニュアルの**番号の引き継ぎ** | マニュアルが親フローのステップから1クリックで開ける |
| **2** | フローに**5W2Hの欄** | How欄が空のステップが一覧で出る |
| **3** | **実行の記録（D）**＋携帯アプリ化＋名前の確定 | 「誰が・いつ・どのステップをやったか」が貯まり始める |
| **4** | **評価の自動判定**（周回数・ノウハウ化・定着） | ステップごとに4つの力が自動で出る |

## 点検（配る処理に埋め込む）

`--deploy` のたびに、次の3つを一覧に出す。**通らないと配れない形にする。**

1. **材料の宣言（`flow-source`）が無いフロー** → 古くなっても気づけない
2. **親のステップへ戻れないフロー** → 上下が切れている
3. **How欄が空のステップ** → マニュアルが無い場所

**手順書に書かない。通り道に置く。**（`common-rules` 項5・CLAUDE.md 第5条）
